Tyr: types as part of the machine-learning system

Tyr is an experimental machine-learning and scientific-computing system written in Lean 4. It investigates which assumptions can be made explicit in the program, while retaining practical tensor, model, solver, and GPU execution paths.

Christian Pehle

Abstract

Machine-learning programs distribute structural assumptions across source code, checkpoint metadata, compiler configuration, and runtime assertions. A tensor operation may only be defined for a particular shape, a checkpoint field may be required by a model, and a generated kernel may only be valid on a subset of devices. These conditions are often discovered only when the corresponding path is executed.

Tyr explores a different arrangement. Tensor shapes and dtypes can enter Lean types; checkpoint headers can generate typed declarations during elaboration; solver and event structure can be represented explicitly; and GPU capabilities can constrain kernel programs before code generation. The system uses native numerical backends where appropriate. It is a research codebase, not a production framework, and the examples below distinguish static guarantees from runtime tests.

Scope. “Typed” does not mean that floating-point results are formally verified. Tyr combines static contracts, runtime validation, and numerical comparison. Each figure states which layer it exercises.

Why dependent types?

Many assumptions in an ML program are relations between values: the output width of one layer must equal the input width of the next; two operands must have compatible dtypes and devices; a reshaped tensor must contain the same number of elements. An ordinary tensor type says that a value is a tensor. A dependent tensor type can also state its shape, dtype, or device policy, because values such as dimensions occur in the type itself.

This changes when consistency is checked. Instead of rediscovering a wiring error in one particular batch at runtime, Lean checks the relationship while elaborating the program. The relationships then compose: if one function returns Tensor #[batch, hidden] and the next requires that shape, their connection is checked wherever the functions are assembled, including when batch and hidden are still symbolic.

The point is not to place every property of a learned system in a type. Data-dependent dimensions, imported checkpoints, device availability, allocation, and floating-point behavior still cross runtime boundaries. The useful division is to make stable structural relations static, validate external data when it enters the system, and leave numerical execution to numerical backends.

A shape-dependent operation

The contract for a linear projection makes the relationship visible. The same m occurs in the activation and weight types; b is preserved; and n, taken from the weight, becomes the output width. The dtype and device policy must also agree.

def linear {m n b : UInt64} {d : DType} {dev : DevicePolicy}
    (x      : Tensor ⟨#[b, m], d, dev⟩)
    (weight : Tensor ⟨#[n, m], d, dev⟩) :
    Tensor ⟨#[b, n], d, dev⟩ :=
  .assumeSpec (torch.linear x.raw weight.raw)

A use site can specialize this contract to ordinary model dimensions. The valid program below elaborates. Changing the weight from #[512, 768] to #[768, 512] makes the shared input dimension inconsistent, so Lean rejects the program before a numerical kernel is called.

What is compiled, and what runs?

For this example, Lean first elaborates project and unifies the dimension variables in linear. In the valid case it resolves b = 32, m = 768, and n = 512. The invalid case cannot assign one value to the two occurrences of m, so compilation stops at this stage.

The accepted program does not carry a second, shape-rich tensor representation at runtime. Tyr’s Tensor σ is a typed view whose StaticSpec index is phantom; its only field is the existing raw tensor handle. Lean then compiles the ordinary program and its call to the external symbol lean_torch_linear. The C++ bridge passes the two tensor handles to torch::linear, and LibTorch dispatches the operation according to the tensors’ actual placement.

Thus the type checker establishes the wiring relation, while LibTorch remains responsible for allocation and numerical execution. The lower-level typed GPU language discussed later is a separate path: it generates CUDA rather than calling this LibTorch operator.

Differentiation through a contact event

Hybrid systems combine continuous dynamics with discrete state changes. In the example below, a sphere described by a small URDF falls under gravity and collides with a plane. Tyr localizes the contact at τ = 0.2, applies the velocity reset, and propagates the adjoint through the event with a saltation update.

The plotted trajectory is exported by the Lean executable at 5 ms intervals. Both one-sided states at the event are retained. Consequently the discontinuity in velocity is shown as a jump rather than being smoothed by the visualization.

Checkpoint schemas during elaboration

A second use of Lean’s elaborator concerns model data rather than tensor operations. The SafeTensors type provider reads a checkpoint header while compiling a module and generates tensor specifications, checked loaders, and a nested record corresponding to the checkpoint hierarchy.

Practical model execution

Tyr also contains model, tokenizer, sharded-checkpoint, and generation code for current transformer families. This is less specific to Lean than the previous examples, but it tests whether the typed surface remains connected to a practical runtime.

For the recorded run below, Tyr loaded a Qwen3.6 27B checkpoint and generated tokens through the ordinary Device.CUDA 0 path. This is a runtime integration example; neither the model implementation nor the device abstraction is specific to the accelerator used for the capture.

GPU programs and capability constraints

There are two relevant layers. Tensor programs carry an explicit device, and the runtime represents CPU, CUDA, and MPS targets. The lower-level kernel compiler currently targets NVIDIA CUDA. It contains a typed tile language, architecture capability classes, code generation, native dispatch, and parity tests against numerical references. This path is not tied to the GB10 used for recorded launch workloads. The local compiler-side suite currently contains 49 tests covering constrained matrix multiplication, reductions, online softmax, barriers, attention structure, Brownian sampling, and Runge–Kutta code generation.

Execution tests remain hardware-specific measurements. Their results should therefore name the generated kernel, device, reference, tolerance, and actual dispatch route. A passing test on one device is evidence for that path, not a claim about every GPU.

Current direction

Tyr is an attempt to use Lean as part of an ML system rather than only as a language in which isolated tensor identities are proved. The useful question is not whether every numerical property can be encoded in a type. It is which contracts become clearer or cheaper to enforce when the model, compiler, solver, checkpoint schema, and kernel description share one language.
